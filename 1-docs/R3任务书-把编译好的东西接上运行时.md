## 0. 这一轮要解决的是什么

编译侧已经完整：`md → 解析 → 编译 → 唯一投影 → lint`。任务图装好了 87 个角色节点＋阶段任务节点，`前置`／`遍历模式`／`失败处理`／`推进方式` 都能写、能校验、能进图。

**但没有一处代码读它们。** 运行时推进仍是 `service.js:1008` 的 `session.currentTaskIndex += 1`。

后果不是"少个高级功能"，而是**主流程有两处真实卡死**（下面 R3-0 是本轮排查新发现的，比图执行器更紧急）：

### 排查结论：两个 advanceMode 分支设了标记但无人消费

`finalizeToolResult`（`service.js:999-1018`）有三条分支：

```js
if (task.advanceMode === 'teacher') {
  session.events.push(`${completedId}:waiting-teacher-advance`);
  input.data.waitingForTeacher = true;          // ← 全仓没有第二处引用
} else if (task.advanceMode === 'ai_suggest') {
  session.events.push(`${completedId}:waiting-student-advance`);
  input.data.waitingForStudent = true;          // ← 全仓没有第二处引用
} else if (session.currentTaskIndex < role.tasks.length - 1) {
  session.currentTaskIndex += 1;                // ← 只有这一条真的推进
}
```

实测（`grep -rn 'waitingForTeacher\|waiting-teacher-advance' server/ src/`）：**除了这两行赋值，全仓零引用**。学生做完任务后进度停住，且：

- 教师端 13 个指令里**没有 `advance_task`**——老师手上没有能解开它的按钮；
- `skip_step` 解不了：它走 `task_step_completed`，而小步走完只是 `setDialogueLifecycle('WAIT_FOR_TOOL_RESULT')`（`service.js:716`），任务推进的唯一入口仍是 `finalizeToolResult`。

**存量影响**：5 门课 87 个任务里，85 个是 `auto_after_validation`（正常），**2 个写着 `推进方式：teacher`**：

- `6-lessons/lesson_zhizhi_001/roles/assembly-speaker.md:89`
- `6-lessons/lesson_zhizhi_001/roles/id-designer.md:155`

这两个任务今天一旦被学生做完就**永久卡住**，现场只能重开会话。`ai_suggest` 存量为 0，但字段合法、spec 里写着可用，课程团队随时会写。

## 2. R3-0：修两个 advanceMode 卡死

### 2.1 `advance_task` 教师指令（对应 `teacher` 分支）

跨墙仍走「学生端作为桥」——**不给 `course-run-service.js` 加任何 import**（它至今只有 `node:crypto` 一行，这是硬约束）：

```
教师点「推进任务」→ 场次记录 → 学生端轮询 → applyTeacherCommand
  → runAgentTurn({ type: 'lifecycle_event', event: 'teacher_advance_task', data: { taskId, teacherCommandId } })
  → service.js 校验后推进 session.currentTaskIndex
```

落点：

1. `server/runtime/course-run-service.js`：`advance_task` 加入指令白名单与审计，标 `HIGH_IMPACT`（它会真推进学生进度）。
2. `src/app-controller.js` 的 `applyTeacherCommand`：加 `advance_task` 分支，照 `skip_step` 的写法发 `lifecycle_event`。
3. `server/agent/service.js`：新增 `teacher_advance_task` 生命周期分支，**只在 `waiting-teacher-advance` 状态下生效**——否则老师可以随手把学生推过没做的任务。

**合法性校验，不做教学判断**（沿用 T1 的口径）：`taskId` 必须等于学生当前任务，且该任务必须已完成（`completedTaskIds` 含 `${role.id}:${task.id}`）。不满足就返回明确错误，不静默降级。

### 2.2 学生自主推进（对应 `ai_suggest` 分支）

`ai_suggest` 的语义是"AI 建议、学生确认"。已完成但等确认时给学生一个「继续下一个任务」入口，点了走 `lifecycle_event: student_advance_task`，同一套校验。

⚠️ 存量 0 使用，但**不能因此不做**——字段在 spec 里标着可用，课程团队写了就会卡死。要么实现，要么从 spec 删掉；选实现。

**实现时改了落点：按钮做在任务卡上，不做成 quickReply。** 原计划写的是 quickReply，实际不行——快捷回复在下一条消息进来时会被清掉（`app-controller.js` 里三处 `filter(type !== 'quick-replies')`），而等待推进可能持续很久，学生一旦发过一句话按钮就没了，又卡回去。任务卡是常驻的，等待态从 `state.updated.pendingAdvance` 读，刷新页面也还在。

### 2.4 完成情况（2026-08-08）

6 例全绿；牙齿验证实测第 2、3、4、6 例变红，第 1、5 例仍绿（它们不经过该分支，正确）。全量 **297/297**，`npm run build` 与根 `npm run verify` 通过。

排查中另外补了两处，都是"卡死换个位置"而不是新功能：

- **`appendStateDrivenTools` 的入口条件**：它原本只认 `tool_result`，而推进解除走的是 `lifecycle_event`。不补的话老师按了确认、进度确实 +1，但**新任务的工具卡永远不开**，学生停在一张已完成的旧卡上。
- **`turn-router.js` 给推进回合走 `silent`**：否则它落到通用 `lifecycle_event` 分支真调一次主模型，而这一轮没有新话可说，反重复层会把回复替换成"这句话我刚才说过了"——学生看到的是一句莫名其妙的抱怨。实测补完后推进回合主模型调用数为 0。

## 3. R3-1：收敛推进语义（行为不变）

`currentTaskIndex` 现在有 **38 处引用**（`grep -c` 实测），其中读取占绝大多数，真正**写**的只有 3 处：`session-factory.js:24`（初始化 0）、`service.js:1008`（+1）、R3-0 新增的两处。

但"读"里藏着重复的语义，散在 4 处以上：

```js
role.tasks[Math.min(session.currentTaskIndex, role.tasks.length - 1)]   // service.js 出现 9 次
role.tools.find((item) => item.taskIndex === session.currentTaskIndex)  // 出现 4 次
```

**做法**：新建 `server/agent/task-advance.js`，导出三个纯函数：

- `currentTaskOf(role, session)` —— 收敛那 9 处 `Math.min`；
- `canAdvance(role, session, task)` —— 三种 advanceMode 的判定；
- `advanceTask(role, session)` —— 唯一的写入点，返回 `{ advanced, nextTask, reason }`。

**这一步严禁改变任何行为**。验收方式是"改完 282 例一个不动"——包括 `tests/task-graph.test.js` 那条"图遍历与 `currentTaskIndex += 1` 完全一致"的等价性断言。

## 4. R3-2：`advanceTask` 换成读图

`task-graph.js` 的 `traversalOrder(graph, roleId)` 已经保证：入度为 0 的节点按 `taskIndex` 起步，**线性课程的结果与今天逐个 +1 完全一致**（`tests/task-graph.test.js` 现有断言，29 个角色全覆盖）。这是切换的等价性保证。

改法：`advanceTask` 内部从"下标 +1"换成"在 `traversalOrder` 里取当前节点的下一个，且其 `prerequisites` 全在 `completedTaskIds` 里"。`currentTaskIndex` **保留**为对外契约（`app.js:82`、`learning-view.js`、前端 `roleState.progress` 都在用），只是不再是推进的依据——它变成"当前任务在遍历序列里的位置"。

验收：5 门课 29 个角色的遍历序列与 R3-1 之前**逐条相同**；`前置` 写错（指向不存在的任务）时报错不静默丢边（图装配已有 `unknown_prerequisite` 告警，这里要确认运行时也不会因此卡死）。

## 5. R3-3：`遍历模式：open`

`course.md` 写 `遍历模式：open` 时，学生可在**所有已解锁任务**间自选（解锁 = `前置` 全部完成）。

- 5 门课当前全是 `sequential`，因此这一块**对存量零影响**——必须有测试钉住这一点；
- 闯关线只渲染 `sequential`（spec §9 的复杂度约束），`open` 只影响对话线；
- 需要一个 `open` 的测试课程 fixture（内存构造，不新增 `6-lessons/` 目录）。
