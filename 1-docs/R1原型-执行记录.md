## 3. 任务书与代码不符之处（**执行时按代码为准，未修改任务书**）

### 3.1 `llm.generate` 没有 `timeoutMs` 参数

任务书 §3.4 写"若 llm.generate 自带超时/abort 机制按真实接口用，否则用 Promise.race 包一层"。

实际接口（`server/services/llm.js:164`）：`generate({ instructions, messages, tools, images, jsonMode, maxRetries, onTextDelta, signal })`——**只有 `signal`，没有 `timeoutMs`**。超时是在工厂层 `createLLM({ timeoutMs })` 设定的，默认 18 秒，比本模块要求的 8 秒预算长得多。

处理方式：**两者都做**。
- 传 `AbortController` 的 `signal`，让真实 HTTP 请求能被真正取消（只用 Promise.race 会让底层请求继续跑到 18 秒，造成连接与 token 浪费）；
- 外层再用 `Promise.race` 兜底，保证即使底层不响应 abort（例如测试里永不 resolve 的 mock），本模块也一定在预算内返回。

⚠️ 如果这份任务书还要发给别的 agent 执行，建议把 §3.4 改成明确指令，否则容易只写 Promise.race 而留下请求泄漏。

### 3.2 禁区清单 §7 遗漏了 `server/agent/turn-understanding.js`

这是现有文件（74 行），功能与新建的 `understanding.js` **高度重叠**：它已经在做 jsonMode 结构化回合理解，只是被限制在"有待答问题时才调用"。我没有碰它，也没有 import 它。

## 4. 我做的设计判断（任务书未明确，**需要你确认**）

### 4.1 ⭐ 防复读两条子规则撞车时，强制换档优先

任务书 §4 规则 7 有两条子规则，在同一个场景下会同时命中：

> 场景：`recentActions` 末尾连续两次 `give_scaffold`，第三次又来同类求助。
> - 子规则一说：同类求助第二次 → `give_scaffold` + `scaffoldLevelDelta:+1`
> - 子规则二说：连续 2 次同一 action → 第三次强制换成 `redirect_task`

§5 的测试用例只覆盖了"第二次"（子规则一）和"reply_natural 连三次"（子规则二），没有锁定交叉点。

**当前实现：强制换档优先，升档让位**（第三次输出 `redirect_task`，`params` 为空）。理由是子规则二在任务书里被标注为"防复读强制换"，而防复读正是这个模块存在的核心理由；第三次还给提示，即使内容升了档，学生感知上仍是"又给提示"。

已写成测试 `连续两次脚手架后第三次同类求助：强制换档优先于升档`，并在测试文件里加了注释标为待确认。**如果你倾向"升档优先"，改动量只有 `decideTutorAction` 里两行调用顺序 + 那一条测试断言。**

### 4.2 8 秒是总预算，不是单次预算

任务书 §3.4 说"总预算 8 秒"，§3.5 又说失败要"重试一次"，两者组合有歧义。

**当前实现**：8 秒覆盖"首次调用 + 一次重试"。每次尝试拿到的是剩余预算；预算耗尽就直接返回保守缺省、不再重试。所以：
- 模型快速抛错 → 调用 2 次（几乎不耗预算）
- 模型挂起 → 调用 1 次（首次就吃掉全部预算）

这样 §5.2（断言调用 2 次）和 §5.4（挂起→缺省）都成立。如果你要的是"每次 8 秒、最坏 16 秒"，改 `understandTurn` 里预算计算那 3 行即可。

### 4.3 zod 校验的宽严尺度

- **严格拒绝**（触发重试→缺省）：`intent`/`emotion` 不在枚举内、`answersPendingQuestion` 不是真布尔值。需要保留一条明确的"校验不过"路径，否则 §5.3 那条测试无从触发。
- **宽容处理**：`confidence` 用 `z.coerce.number()` 收字符串数字，再夹到 0–1（模型返回 1.7 → 收敛为 1，不判失败）；`want` 可缺省、超 200 字截断。

### 4.4 两个意图没有对应的决策规则

§4 的 6 条决策规则没有覆盖 `asking_knowledge` 和 `answering_question`（且 `answersPendingQuestion` 为 false）在高置信度时的走向。

**当前实现**：兜底为 `reply_natural`，reason 写明"由回应生成层决定是否检索课程知识"。因为 `TUTOR_ACTIONS` 五个动作里没有"走知识检索"这一项，检索与否应由第三段（生成层）根据 intent 决定，不该在决策层硬编码。**接线时请确认生成层会读 `understanding.intent` 而不是只读 `action`。**

### 4.5 `context.idleSeconds` 未被使用

契约里有这个字段，但 §4 的 6 条规则没有一条用到它。我保留了字段但不消费。如果原意是"空闲太久也要换策略"，需要补一条规则。
